# 普润制衣团购仓平台

项目已经拆成三个独立部分：

- `miniapp/`：微信小程序用户端
- `server/`：商品 API、SQLite 数据库和图片存储
- `server/public/admin/`：商品管理后台

## 现在如何查看效果

### 1. 打开商品管理后台

双击根目录的 `启动管理后台.cmd`，浏览器会自动打开：

`http://127.0.0.1:3000/admin/`

本地演示密码：`admin123`

可以进行：

- 新增、编辑和删除商品
- 修改款号、名称、分类、价格、颜色、尺码等信息
- 按 S、M、L、XL 等尺码修改库存，总库存自动汇总，并查看尺码库存预警
- 下载 Excel 库存模板，按款号和尺码批量导入库存；错误行会整份回滚并提示具体原因
- 上传多张 JPG、PNG 或 WebP 图片；商品图片统一存成 JPG（透明背景的存 PNG），不存 WebP，方便客户保存原图、电脑版微信转发成图片
- 保存为草稿，或控制商品上架/下架
- 搜索商品并按发布状态筛选

### 2. 在微信开发者工具查看小程序

项目已经导入微信开发者工具，工具版本为 Stable v2.01.2510290。

1. 先启动管理后台。
2. 打开微信开发者工具中的 `App` 项目。
3. 点击顶部“编译”，或在模拟器中刷新页面。
4. 首页、分类页和商品详情页会读取后台中“已上架”的商品。
5. 管理后台保存商品、分类、轮播图、图片或库存后，小程序重新进入相应页面即可读取最新数据，不需要重新编译或重新审核。

如果需要停止本地服务，双击 `停止本地服务.cmd`。

## 已实现功能

小程序端：

- 首页品牌横幅和动态商品分类
- 文字搜索与拍图识别商品、分类、价格排序和商品列表
- 商品画册、价格、颜色和尺码
- 无需登录即可浏览、搜索、查看库存和使用设计功能
- 首页和分类页展示总库存，详情页展示每个尺码的实时库存、低库存及缺货状态
- 商品页提供独立详情页和实拍图页，可查看详情文案、详情长图及分类实拍图
- 在线服装设计演示
- 个人中心
- 后端短暂不可用时优先使用最近一次成功加载的服务器缓存，不展示过期演示商品
- 首页、分类和商品详情采用版本化缓存、固定骨架和稳定图片占位；列表使用缩略图，点进商品后再加载清晰图
- 首页、分类、商品、详情和实拍图可下拉刷新：后台保存成功后，下拉会直接向服务器确认数据版本并取回改动；在一个页面刷新到的改动，回到其他页面（含设计）时自动显示
- 图片切换采用双缓冲，新图加载完成前保留旧图，避免轮播、颜色切图和页面首屏出现白闪
- 首页、分类、设计、我的是同一个页面（`pages/home/home`）里的四个分区，由页面自带的底部栏切换：离开的分区在看不见时回到起点（首页回顶部；分类从首页回来时显示全部商品），回来时不闪不跳。旧的 `pages/category`、`pages/designer`、`pages/profile` 地址仍可打开，会转到对应分区

管理端与后端：

- 管理员密码登录与会话保护
- 所有已登录后台账号均可覆盖导入库存；只有主管理员可管理后台账号
- 登录失败限速：同一来源连续输错 5 次后暂时锁定 15 分钟
- 商品新增、查询、编辑、上下架和删除
- 团购价作为默认价，并可按商品尺码顺序设置多个不重叠的特殊尺码区间价
- 库存编辑、低库存统计与 SQLite 持久化
- 图片上传与本地存储
- 保存商品、分类或店铺设置后，自动删除已不再被任何内容引用的旧上传图片；共享图片不会误删
- 粘贴外部 HTTPS 图片链接时先下载到本服务器，数据库仅保存 `/uploads/...` 本地路径，不依赖原图片站点
- 商品主图、详情长图和带分类的实拍图分别管理
- SQLite 持久化数据库
- 小程序公开商品接口
- 拍图识别先使用百炼 `tongyi-embedding-vision-plus` 从自有商品图库召回候选（对“和很多商品都很像”的图片做相似度校正），检索第一名不够明确时再由百炼通义千问视觉模型复核前 8 个候选；任一外部接口不可用时自动降级，传统本地图片索引作为最终兜底
- 自动化接口测试
- 每日生成 SQLite 一致性备份并清理超过 5 天的旧备份；同时清理超过 24 小时仍未被使用的上传图片

抖店库存同步（只有主管理员能看到和操作）：通过独立的 `cpminiapp-douyin.service` 运行，和小程序 API 分开进程、分开资源组；同步服务 CPU 最多使用 0.75 个核，内存软上限 900MB、硬上限 1GB。`cpminiapp-douyin-sync.timer` 仅在每天北京时间 21:00 启动一次，使用当时的小程序最新库存（每个 SKU 最多 20 件）；同一天即使任务失败或服务重启也不会再跑，错过时间不会补跑。扫码只更新登录，导入库存不触发抖店同步，不再自动失败重试，后台取消立即同步。登录有效时不再每天弹出扫码窗口；失效时请在后台扫码，等待下一次 21:00 同步。独立服务使用权限为 0600 的本机 Unix socket 与 API 通信，复用已有登录资料、商品对应和同步历史。

部署隔离同步服务（代码更新到 `/opt/cpminiapp` 后）：

```bash
sudo bash /opt/cpminiapp/deploy/apply-douyin-isolation.sh
systemctl list-timers cpminiapp-douyin-sync.timer
```

本地如需使用后台的抖店登录功能，另开终端运行 `node server/douyin-worker.mjs`；公开商品服务不依赖同步服务是否启动。 用户明确要求立即补同步时，可安装并手动启动 `deploy/cpminiapp-douyin-once.service`；它与常驻同步服务互斥，执行后自动恢复常驻服务，不修改每日定时器。此服务不启用自动调度，运行原因记为“用户授权补同步”。 同步页的记录统一显示北京时间，并明确显示最近一次成功时间。抖店商品列表加载较慢时，脚本等待真实工具栏可见后再打开 Excel 导入菜单；商品页与批量记录分开窗口，导出后保留原导入窗口，避免反复加载商品页导致菜单消失。同步浏览器不加载商品图片或媒体以降低资源占用；错误记录会包含失败阶段。检查脚本 `scripts/check-douyin-sync.mjs` 使用浏览器资料的临时副本和 SQLite 一致性快照，验证模板导出、库存差异和保留的导入窗口，不上传、不提交库存文件。

库存名称对应关系会长期保存在 SQLite 中。同一个“来源名称 + 内部编码”可人工对应一至两个小程序商品，并为每个商品分别选择颜色。首次处理完“库存对应”页面的待对应项并保存后，后续每日上传含相同来源名称和内部编码的 Excel 会自动复用人工对应，同时更新这两个商品；新出现的名称会再次进入待对应列表。

## 本地与正式上线的区别

本地开发使用 `http://127.0.0.1:3000`。它只适用于电脑上的微信开发者工具，手机预览不能访问电脑自身的 `127.0.0.1`。

正式环境当前使用 `https://cpminiapp.xinghaiapp.top`：SQLite 数据库与全部商品图片均保存在自有服务器，微信公众平台请求域名也使用该域名。上线维护时需要继续执行强管理密码、固定会话密钥和定期备份。

图片向量召回与智能复核都只在后端启用，密钥不能写入小程序或提交到 Git。配置项见 `deploy/cpminiapp.env.example`。正式链路使用百炼 `tongyi-embedding-vision-plus-2026-03-06` 1152维向量召回并做相似度校正（撞脸扣分权重 0.5、仓库实拍图额外扣 0.06，`VISUAL_EMBEDDING_HUB_WEIGHT`、`VISUAL_EMBEDDING_REAL_PHOTO_PENALTY`），每款最多收 40 张图进识别库（实拍图最多 15 张、每个颜色都收）。这两项和收图数量是按店里确认过答案的 43 次真实识别调的：正确款出现在结果前 3 个的从 23 次提高到 31 次，第一名正确的约 20 次没有变化；检索第一名领先第二名不足 0.03（`IMAGE_RERANK_SKIP_LEAD`）时，再用 `qwen3.6-plus`（关闭深度思考）复核前 8 个候选（640 像素），复核和向量检索共用同一个百炼密钥。复核时每个候选给的是它和客户照片最像的整件衣服图（商品图、颜色图或实拍图，`IMAGE_RERANK_PICTURES=whole`），不给详情页的局部特写：只看到拉链、领口或背影时，模型没法比较衣服结构。复核时每个候选也附上它的颜色名，模型从选中那款的颜色里原样挑出照片里的颜色（`best_color`）；没复核或挑不出时，用这款最像照片的那张颜色图的颜色。从拍图识别结果点进商品时，商品页直接切到这个颜色。在店里 120 张测试图上，第一名正确的从 34 张（`qwen3-vl-embedding` + `qwen-vl-max`，后者已于 2026-10-10 下线）提高到 45 张。任何一层超时、繁忙或额度不足都会自动降级；部分真实识别会保存为案例（`DATA_DIR/recognition-cases`：缩小的照片和当时的识别结果，没把握的全存、有把握的抽样，最多 400 条、保留 60 天），以后据此改进识别；复核出错时服务日志会写明原因（例如 HTTP 401 密钥失效），方便及时发现。

详细设计见 [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)。

## 自动验证

安装 Node.js 22.5 或更高版本后运行：

```powershell
pnpm test
```

测试覆盖管理登录、商品新增、图片上传、编辑、上架、公开查询和删除。

首次启用视觉向量识别，或需要强制重建全部商品图片向量时运行：

```bash
npm run build:visual-index
# 强制忽略已有向量重新计算
node scripts/build-visual-embedding-index.mjs --force
```

平时新增、换图、删除或上下架商品后，服务会在后台增量更新向量索引，不重复计算未变化的商品图片。

生产服务器启用 `deploy/cpminiapp-maintenance.timer` 后，每天会执行：

```bash
node scripts/daily-maintenance.mjs
```

默认每天保留最近 5 天数据库备份，并给未保存完成的新上传图片保留 24 小时缓冲期。

首次部署高清图片预览，或批量导入历史商品图片后，执行以下命令预生成点开图片后看到的 2000px 高清大图，避免用户首次点击时等待服务器临时处理。大图用 JPG（`/api/product-thumbnail.jpg`）：电脑版微信会把 WebP 图片当成文件转发，JPG 才能直接转发成图片。新上传的图片会自动生成。

```bash
node scripts/build-image-thumbnails.mjs --format=jpg
```

该任务默认并发处理 2 张图片；服务器资源较充足时可使用 `node scripts/build-image-thumbnails.mjs --concurrency=4`。

小程序的商品大图、首页轮播、详情图和实拍图统一按 960px 宽显示。新上传的图片会自动生成该尺寸；历史图片需执行一次以下命令补齐，避免用户首次打开时等待服务器临时缩图：

```bash
node scripts/build-image-thumbnails.mjs --size=960
```


## 性能诊断日志与保留策略

Nginx 的结构化访问日志在 `/var/log/cpminiapp-nginx/access.log`，覆盖商品接口、缩略图和原图下载。每条包含请求 ID、状态码、传输字节、请求总耗时、后端连接/首字节/完整响应耗时；不记录请求正文、Cookie、认证头或完整查询字符串。响应头 `X-Request-ID` 可关联应用中的慢请求和客户端中断记录。

API 与抖店独立进程每 60 秒各写一条 JSON 资源摘要：进程及资源组 CPU、进程及资源组内存（同步资源组包含 Chromium）、主机 CPU/空闲内存、事件循环 p99/最大延迟、请求量、慢请求、异常和客户端中断。超过 1 秒的请求和失败请求额外记录明细；每个进程每分钟最多 30 条明细，超出仅累计计数，避免异常流量放大日志。

运行日志通过 journald 保留最多 7 天，服务器 journal 总容量目标上限 256MB（临时日志 64MB），单文件 16MB、至少每天轮转。该策略也覆盖系统消息及已有 journal，部署会清理超过保留时间或容量的旧 journal。Nginx 新日志每日轮转，超过 16MB 时提前轮转，每 10 分钟检查；每个文件保留最多 7 份压缩归档，超过 7 天的归档每次检查都会删除。高流量时保留时间可能缩短；活动文件在两次检查之间可能暂时超过阈值。

```bash
sudo bash /opt/cpminiapp/deploy/apply-observability.sh
journalctl -u cpminiapp -u cpminiapp-douyin --since '10 minutes ago' --no-pager
sudo tail -n 20 /var/log/cpminiapp-nginx/access.log
systemctl list-timers cpminiapp-logrotate.timer
node server/diagnostics.test.mjs
```
